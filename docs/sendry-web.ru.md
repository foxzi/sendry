# Sendry Web

Веб-интерфейс для управления серверами Sendry.

## Возможности

- Управление шаблонами с версионированием и деплоем
- Управление списками получателей с импортом CSV/JSON
- Управление кампаниями с поддержкой A/B тестирования
- Управление рассылками с паузой/возобновлением/отменой
- Поддержка нескольких серверов с балансировкой нагрузки
- Мониторинг серверов (очередь, DLQ, домены, sandbox)
- OIDC авторизация (Authentik, Keycloak и др.)

## Установка

Sendry Web входит в состав пакета sendry. После установки:

```bash
# Запуск сервиса
sudo systemctl enable sendry-web
sudo systemctl start sendry-web
```

## Конфигурация

Файл конфигурации: `/etc/sendry/web.yaml`

### Базовая конфигурация

```yaml
server:
  listen_addr: ":8088"
  tls:
    enabled: false
    cert_file: "/etc/sendry/certs/web.crt"
    key_file: "/etc/sendry/certs/web.key"

database:
  path: "/var/lib/sendry-web/app.db"

logging:
  level: info    # debug, info, warn, error
  format: json   # json, text
```

### Авторизация

Sendry Web поддерживает два метода авторизации:

#### Локальная авторизация

```yaml
auth:
  local_enabled: true
  session_secret: "ваш-секретный-ключ-минимум-32-символа"
  session_ttl: 24h
```

Создание локальных пользователей через CLI:

```bash
sendry-web user create --email admin@example.com --password secretpassword
```

#### OIDC авторизация

```yaml
auth:
  local_enabled: false  # можно true для fallback
  session_secret: "ваш-секретный-ключ-минимум-32-символа"
  session_ttl: 24h

  oidc:
    enabled: true
    provider: "Authentik"  # отображаемое имя на странице входа
    client_id: "sendry-web"
    client_secret: "ваш-client-secret"
    issuer_url: "https://auth.example.com/application/o/sendry-web/"
    redirect_url: "https://panel.example.com/auth/callback"
    scopes:
      - openid
      - profile
      - email
    allowed_groups:  # опционально, пустой = доступ всем авторизованным
      - "sendry-admins"
```

### Серверы Sendry

Настройка подключения к серверам Sendry MTA:

```yaml
sendry:
  servers:
    - name: "mta-prod-1"
      base_url: "https://mta-1.example.com"
      api_key: "ваш-api-ключ"
      env: "prod"
    - name: "mta-stage"
      base_url: "https://mta-stage.example.com"
      api_key: "ваш-api-ключ"
      env: "stage"

  multi_send:
    strategy: weighted_round_robin  # round_robin, weighted_round_robin, domain_affinity
    weights:
      mta-prod-1: 3
      mta-stage: 1
    domain_affinity:
      "example.com": "mta-prod-1"
    failover:
      enabled: true
      max_retries: 2
```

## CLI команды

### Управление сервером

```bash
# Запуск сервера
sendry-web serve -c /etc/sendry/web.yaml

# Проверка конфигурации
sendry-web config validate -c /etc/sendry/web.yaml
```

### Управление пользователями

```bash
# Создание пользователя
sendry-web user create --email admin@example.com --password secret

# Список пользователей
sendry-web user list

# Удаление пользователя
sendry-web user delete admin@example.com

# Сброс пароля
sendry-web user reset-password admin@example.com
```

### Управление базой данных

```bash
# Запуск миграций
sendry-web migrate

# Очистка старых данных
sendry-web cleanup --days 30              # удалить элементы старше 30 дней
sendry-web cleanup --days 90 --dry-run    # предпросмотр удаления
```

## Веб-интерфейс

### Шаблоны

- Создание и редактирование email шаблонов с HTML редактором
- История версий с возможностью сравнения
- Деплой шаблонов на серверы Sendry
- Предпросмотр с подстановкой переменных

### Получатели

- Создание списков получателей
- Импорт из CSV или JSON
- Экспорт в CSV
- Персональные переменные для каждого получателя
- Отслеживание статуса (active, unsubscribed, bounced)

### Кампании

- Создание кампаний с настройками отправителя
- Переменные уровня кампании
- A/B тестирование с несколькими вариантами
- Распределение трафика по весам

### Рассылки

- Создание рассылок из кампаний
- Планирование на будущее время
- Dry-run режим (тест на первых N получателях перед полной отправкой)
- Мониторинг прогресса в реальном времени
- Операции паузы, возобновления, отмены
- Повторная отправка неудачных элементов
- Ошибки доставки по типам (блок «Delivery Errors» на странице рассылки)

#### Типы ошибок доставки

Тип не хранится в базе: панель определяет его по тексту ошибки от MTA при каждом открытии страницы
(`internal/web/stats/errors.go`). Порядок проверки: ошибки до SMTP-ответа (DNS, подключение, TLS),
затем слова про блок-листы и спам, затем расширенный код (`5.1.1`), затем обычный код (`550`),
затем ключевые слова.

| Тип в панели | Тип из ТЗ | Типичные признаки |
|---|---|---|
| Address does not exist | адрес не существует | `5.1.1`, `5.1.3`, `5.2.1`, `551`, `553`, «user unknown» |
| Mailbox full | почтовый ящик переполнен | `x.2.2`, `552`, «quota» |
| Temporarily unavailable | временно недоступен | `421`, `450`–`452`, прочие `4.x.x`, грейлистинг |
| Domain unreachable | домен недоступен | нет MX, домен не найден, не удалось подключиться, `5.1.2`, `x.4.x` |
| Rejected by server | письмо отклонено сервером | прочие `5xx` (политики, DMARC, синтаксис) |
| Rejected as spam | письмо отклонено как спам | «spam», «unsolicited» |
| Blocked | блокировка | Spamhaus и другие блок-листы, «blocked», «reputation» |
| Temporary technical error | временная техническая ошибка | TLS и сертификаты, таймауты, свой rate limit, ошибки панели и API |
| Unknown error | неизвестная ошибка | всё остальное |

Колонка **Failed** считает окончательно недоставленные письма, **Retrying** — письма, которые MTA ещё
повторяет (статус `deferred`): панель показывает последнюю ошибку, не дожидаясь окончательного отказа.
Число в таблице ведёт на список писем, отфильтрованный по типу (`/jobs/{id}/items?status=…&error_type=…`).

### Отправки (Send History)

Письма, отправленные через API панели. Статусы:

- `pending` — запись создана, письмо ещё не передано в MTA;
- `queued` — MTA принял письмо в очередь, доставка не подтверждена (в том числе `deferred`: MTA повторяет попытки, последняя ошибка видна сразу);
- `sent` — MTA доставил письмо серверу получателя;
- `failed` — доставка не удалась или панель не смогла передать письмо в MTA.

Статус после `queued` обновляет воркер панели, опрашивая MTA так же, как для писем рассылок. До этого изменения (ветка `fix/starttls-fallback`)
`sent` означал «принято MTA», старые записи с этим статусом не перепроверяются. API-ответ клиенту
по-прежнему возвращает `"status": "sent"` в смысле «принято». Блок Delivery Errors и фильтр по типу
ошибки работают так же, как на странице рассылки (`/sends?status=…&error_type=…`). В мониторинге
`queued` учитывается вместе с `pending`.

### Мониторинг

- Дашборд со статусом серверов
- Управление очередью и DLQ
- Просмотр конфигурации доменов
- Просмотр sandbox сообщений

### Трекинг и отписки

Панель умеет отслеживать открытия и клики и принимает отписки. Публичные адреса `/t/o/`, `/t/c/`, `/u/` работают без авторизации и не проверяются по `server.allowed_ips`.

- Настройки: **Настройки → Трекинг** (проксирующий домен, значения по умолчанию).
- В форме кампании: «Отслеживать открытия», «Отслеживать клики», «Добавлять UTM-метки».
- Отписавшиеся адреса видны в адресной книге с фильтром по статусу «Отписан». Отписка действует только в книге рассылки.
- На странице задания: статистика (Open Rate, CTR, CTOR, отписки) и вкладка «Карта кликов».

Подробности: [Трекинг](tracking.ru.md).

### API панели

Порт панели (по умолчанию 8088), авторизация API-ключом (`Authorization: Bearer <key>` или `X-API-Key`).

```
POST /api/v1/send
POST /api/v1/send/template
GET  /api/v1/send/{id}/status
```

Помимо обычных полей письма (`from`, `to`, `subject`, `html`, `template_id`, `data` и других), запросы на отправку принимают необязательные поля трекинга:

| Поле | Тип | Описание |
|------|-----|----------|
| `track_opens` | boolean | Вставить пиксель открытия. Перекрывает флаг API-ключа |
| `track_clicks` | boolean | Заменять ссылки на трекинговые. Перекрывает флаг API-ключа |

Если поле не передано, действует флаг ключа `track_opens` / `track_clicks` (по умолчанию выключены). Отписки для писем через API нет. Подробности и пример: [Трекинг](tracking.ru.md).

## Подстановка переменных

Шаблоны поддерживают динамическую подстановку переменных с использованием синтаксиса `{{имя_переменной}}`.

### Приоритет переменных

Переменные объединяются при отправке с следующим приоритетом (от высшего к низшему):

1. **Переменные получателя** — индивидуальные данные для каждого получателя из списка
2. **Переменные кампании** — общие значения для всех получателей в кампании
3. **Глобальные переменные** — серверные настройки по умолчанию из раздела Settings

Если одна и та же переменная определена на нескольких уровнях, используется значение с более высоким приоритетом.

### Встроенные переменные

Следующие переменные доступны автоматически:

| Переменная | Описание |
|------------|----------|
| `{{email}}` | Email адрес получателя |
| `{{name}}` | Имя получателя (если указано в списке) |

### Поле Variables (JSON) в редакторе шаблонов

При редактировании шаблона поле **Variables (JSON)** служит двум целям:

1. **Документация** — описывает, какие переменные ожидает шаблон
2. **Тестовые значения** — используются при отправке тестовых писем через кнопку "Test Email"

Пример:

```json
{
  "company_name": "ООО Рога и Копыта",
  "unsubscribe_link": "https://example.com/unsubscribe",
  "promo_code": "ЛЕТО2024",
  "order_id": "12345"
}
```

Это поле не влияет на отправку продакшен писем — оно только для документации и тестирования.

### Примеры использования

HTML шаблона:

```html
<p>Здравствуйте, {{name}}!</p>
<p>Ваш заказ #{{order_id}} отправлен.</p>
<p>Используйте промокод <b>{{promo_code}}</b> для следующей покупки.</p>
<p>Свяжитесь с нами: {{support_email}}</p>
<p><a href="{{unsubscribe_link}}">Отписаться</a></p>
```

### Глобальные переменные

Настройте глобальные переменные в **Settings → Global Variables**. Они доступны во всех шаблонах и могут быть переопределены переменными кампании или получателя.

Типичные применения:
- Название компании и контакты
- Email адреса поддержки
- Ссылки на социальные сети
- URL для отписки
- Юридические оговорки

#### `spf_include`

Специальная глобальная переменная, которая используется в разделе **Domains → Recommended DNS Records** и командой [`dns-sync`](dns-sync.ru.md).

- Ключ: `spf_include`
- Значение: SPF-домен вашего провайдера без `include:` и без `v=spf1`, например `_spf.mailgun.org` или `spf.sendgrid.net`.

Если переменная задана, рекомендуемое значение SPF становится `v=spf1 a mx include:<value> ~all`. Если не задана — используется `v=spf1 a mx ~all`.

## Синхронизация DNS

Sendry Web умеет сравнивать текущие DNS-записи домена с рекомендуемыми SPF, DKIM и DMARC и, при необходимости, создавать или обновлять их через API DNS-провайдера.

Поддерживаемые провайдеры: Cloudflare (API Token или legacy Global API Key), Namedot.

```bash
# Только план (API Token)
sendry-web dns-sync --config /etc/sendry/web.yaml \
  --domain example.com \
  --token "$CLOUDFLARE_API_TOKEN"

# Применить изменения (API Token)
sendry-web dns-sync --config /etc/sendry/web.yaml \
  --domain example.com --apply \
  --token "$CLOUDFLARE_API_TOKEN"

# Применить изменения через Global API Key
sendry-web dns-sync --config /etc/sendry/web.yaml \
  --domain example.com --apply \
  --email "$CLOUDFLARE_API_EMAIL" \
  --token "$CLOUDFLARE_API_KEY"
```

Полное руководство: [DNS Sync](dns-sync.ru.md).

## Безопасность

- Авторизация на основе сессий с настраиваемым TTL
- CSRF защита через state параметр в OIDC
- Безопасные настройки cookie (HttpOnly, Secure, SameSite)
- Контроль доступа по группам через OIDC
- Шифрование API ключей в БД (планируется)

## Устранение неполадок

### Проблемы с OIDC

1. Проверьте доступность `issuer_url` с сервера
2. Убедитесь, что `redirect_url` совпадает с настройками OIDC провайдера
3. Проверьте правильность `client_id` и `client_secret`
4. Смотрите логи для детальных сообщений об ошибках

### Проблемы с базой данных

```bash
# Проверка прав доступа к файлу БД
ls -la /var/lib/sendry-web/app.db

# Запуск миграций вручную
sendry-web migrate -c /etc/sendry/web.yaml
```

### Подключение к серверам Sendry

1. Проверьте доступность `base_url`
2. Убедитесь в валидности API ключа
3. Проверьте доверие к TLS сертификатам
