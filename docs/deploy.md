# Release and Deploy from GitHub Actions

[Русская версия](deploy.ru.md)

How to cut a new Sendry version and roll it out to production servers from GitHub Actions, without manual commits and without logging in to the servers.

## Overview

```
Actions → "Release (button)"  ──tag vX.Y.Z──▶  "Release" (deb, Docker, GitHub Release)
                                                           │
Actions → "Deploy" (version, target)  ──SSH──▶  Ansible upgrade.yml on hosts from inventory/prod.yml
```

Deploy does **not** start automatically after a build. Releasing and deploying are two separate buttons; a rollback is just a deploy of the previous version.

## Step 1. Release: workflow "Release (button)"

File: `.github/workflows/release-button.yml`. Actions → Release (button) → Run workflow (branch `main`):

| Input | Meaning |
|---|---|
| `bump` | `patch` for fixes (0.4.20 → 0.4.21), `minor` for new features or API changes between panel and MTA (→ 0.5.0), `major` for breaking changes (→ 1.0.0) |
| `dry_run` | only print the next version, do not tag |
| `skip_ci_check` | tag even if CI for the commit has not passed (by default a green CI run on HEAD of `main` is required) |

The workflow computes the next version from the latest `vX.Y.Z` tag, creates an annotated tag on HEAD of `main`, pushes it and starts the regular **Release** workflow (`release.yml`) on that tag. `release.yml` builds binaries, packages, the Docker image and the GitHub Release with generated release notes. The run summary lists the version, the commits since the previous tag and links to the build and the release page.

Manual tagging (`git tag v0.4.21 && git push origin v0.4.21`) keeps working the same way.

### Why the build is started explicitly

The tag is pushed with the built-in `GITHUB_TOKEN`, and GitHub deliberately does not fire other workflows on such pushes. `release-button.yml` therefore runs `gh workflow run release.yml --ref vX.Y.Z` right after the push; `release.yml` has a `workflow_dispatch` trigger for this. The result is identical to a manual `git push origin vX.Y.Z`. No secrets are needed for releasing.

### CHANGELOG

Version history lives in **GitHub Releases** (release notes are generated by `release.yml`). The workflow does not modify `CHANGELOG.md`; entries there are added with a regular commit to `main` before pressing the button.

## Step 2. Deploy: workflow "Deploy"

File: `.github/workflows/deploy.yml`. Wait until the **Release** workflow for the tag is green (the release page must contain `sendry_X.Y.Z-1_amd64.deb` and `_arm64.deb`), then Actions → Deploy → Run workflow:

| Input | Meaning |
|---|---|
| `version` | e.g. `0.4.21` (a leading `v` is accepted). Must exist as a GitHub Release with deb assets, otherwise the workflow stops at the first job |
| `target` | `all`: every MTA one by one, then the panel; `mta`: MTA only; `panel`: panel only |
| `limit` | one inventory host (`mx1`, `mx2`, `mx3`, `panel`); empty means all hosts of the group |
| `force_restart` | restart services even if the version is already installed |

Job **Deploy MTA** walks the `sendry_mta` group with `serial: 1`; the panel survives thanks to `multi_send` failover. Job **Deploy panel** runs only after a successful MTA job (or alone when `target=panel`). Two deploys cannot run at once (`concurrency: deploy-production`). Secrets are plain repository secrets; no GitHub environment is required.

On every host the playbook `ansible/playbooks/upgrade.yml`:

1. Reads the installed package version and the list of `sendry` / `sendry-web` services that are **active or enabled** in systemd. Only those are restarted and health-checked.
2. Verifies the services run `/usr/bin/…`. If a unit was overridden to another binary (e.g. `/usr/local/bin/sendry-web`), the playbook fails with an explanation instead of silently leaving the old process running.
3. On the panel, backs up SQLite before installing: `sqlite3 app.db ".backup /var/lib/sendry-web/backups/app-<old version>-<date>.db"`, keeping the newest 5. `sendry-web serve` migrates the database on start and there is no down-migration.
4. Skips the install when the version is already present (re-runs are idempotent and restart nothing). Otherwise downloads the deb from the GitHub Release and installs it with dpkg; downgrades are allowed.
5. Restarts the services from step 1 and waits up to 30 s for HTTP 200 from `/health` (MTA `http://127.0.0.1:8080/health`, panel `http://127.0.0.1:8088/health`, both overridable in the inventory).
6. Prints `sendry version` / `sendry-web version`.

Configs in `/etc/sendry` are never read or modified.

## Rollback

Actions → Deploy with `version` set to the previous release. If the new version already migrated the panel database and the old binary refuses to start, restore the backup by hand:

```bash
sudo systemctl stop sendry-web
sudo ls -l /var/lib/sendry-web/backups/
sudo cp /var/lib/sendry-web/backups/app-0.4.20-1-<date>.db /var/lib/sendry-web/app.db
sudo chown sendry:sendry /var/lib/sendry-web/app.db
sudo systemctl start sendry-web
```

## Inventory `ansible/inventory/prod.yml`

| Inventory name | Group | Host |
|---|---|---|
| `mx1` | `sendry_mta` | `mx1.semena.run` |
| `mx2` | `sendry_mta` | `mx2.semena.run` |
| `mx3` | `sendry_mta` | `sendry-marketing.semena.run` (new MTA, see new-mta-server.ru.md) |
| `panel` | `sendry_panel` | `sendry.soroka.app` |

The file is committed; it contains no secrets. The SSH user is `ansible_user` at the bottom of the file (`deploy`, with `become`). To add an MTA, add a host under `sendry_mta` and install the deploy public key on it.

## One-time setup

### GitHub secrets

Repository → Settings → Secrets and variables → Actions → New repository secret. Collaborators with write access can do this.

| Secret | Value |
|---|---|
| `DEPLOY_SSH_KEY` | private ed25519 key of the deploy user (`ssh-keygen -t ed25519 -f sendry-deploy -C sendry-deploy -N ""`, paste the whole `sendry-deploy` file) |
| `DEPLOY_KNOWN_HOSTS` | optional, output of `ssh-keyscan mx1.semena.run mx2.semena.run sendry-marketing.semena.run sendry.soroka.app`. When set, host keys are verified; otherwise the workflow warns and skips verification |

To require a manual approval per deploy, the owner can create an environment `production` with Required reviewers, move the secrets there and add `environment: production` to both deploy jobs in `deploy.yml`.


### `deploy` user on every server

```bash
sudo useradd -m -s /bin/bash deploy
sudo install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
echo '<contents of sendry-deploy.pub>' | sudo tee /home/deploy/.ssh/authorized_keys
sudo chmod 600 /home/deploy/.ssh/authorized_keys && sudo chown deploy:deploy /home/deploy/.ssh/authorized_keys
echo 'deploy ALL=(ALL) NOPASSWD: ALL' | sudo tee /etc/sudoers.d/deploy
sudo chmod 440 /etc/sudoers.d/deploy
```

Check: `ssh -i sendry-deploy deploy@mx1.semena.run sudo -n true`. Using `root` instead is a one-line change of `ansible_user` in `prod.yml`.

### Panel before the first deploy

- `systemctl cat sendry-web | grep ExecStart` must point to `/usr/bin/sendry-web`. Remove any override to `/usr/local/bin`, delete the stray binary, `systemctl daemon-reload`. The playbook refuses to upgrade while the override exists.
- Decide whether the local `sendry` MTA on the panel is needed; if `web.yaml` has no `localhost` server, `systemctl disable --now sendry`.

### First run by hand

```bash
cd ansible
ansible-playbook -i inventory/prod.yml playbooks/upgrade.yml -l mx1 -e sendry_version=0.4.20 --private-key ~/sendry-deploy
```

Expect the package to update, `systemctl is-active sendry`, `/health` to answer and the panel's Servers page to show the new version. A second run must change nothing. Then `-l mx2`, `-l mx3`, then `-l sendry_panel`.

## Troubleshooting

| Symptom | Where to look |
|---|---|
| Release (button) fails with "CI has not passed" | wait for a green CI run on `main` or set `skip_ci_check` |
| Tag exists but no build | the "Start Release workflow" step failed; run Actions → Release → Run workflow with the tag as ref |
| Deploy fails with "Release vX has no …deb asset" | the build is still running or failed |
| "Permission denied (publickey)" | `DEPLOY_SSH_KEY` does not match `authorized_keys` of the deploy user, or `ansible_user` in `prod.yml` is wrong |
| "runs /usr/local/bin/… instead of /usr/bin/…" | remove the systemd unit override on the server |
| Health check timed out | `journalctl -u sendry -n 50` (or `-u sendry-web`) on the host; roll back by deploying the previous version |
